# Website settings and photo completion

The header links to `website-settings.html`. Owners can manage tag choices, project-owner choices and the default owner. Tags are checkboxes in the project-summary editor; new-project and settings owner selectors use configured choices. Directory filtering includes owners still present on existing projects, even after removal from the available choices. Removing/renaming a choice does not rewrite projects or history. Owner labels do not grant access.

`GET/PATCH /api/project-engine/settings` uses the existing enabled, owner-only, same-origin engine entry. Settings edits carry a loaded revision and compare-and-swap; stale changes are rejected and a matching lost-response retry is harmless. The page retains unsaved input after errors. The global settings row is included by Backup all data. Individual project backups preserve their tags/owner, independent of the current choices, without replacing global configuration.

Engine migration 15 retains the old fixed-choice owner column as an internal compatibility value, adds a canonical owner-name column with bounded text validation and copies existing visible/pending owners. It does not rebuild the parent table, drop foreign keys, change access IDs or delete files/data. Deleting and retired restore headers retain their original compatibility value and remain fenced; they are not republished by the migration. The compatibility column is omitted from public workspace state and project backup formats. Existing tags seed global choices (case-insensitive deduplication; up to 100 valid choices); saved choices outside the list remain available on their original projects.

Photos have explicit Save inside their editing tools. Uploads remain immediate guarded saves; Save closes the tools and updates their open state. The pencil remains an unfilled silhouette, below the photo and aligned to its right edge. A shared geometry module serves overview, gallery, Workshop and entry photos; observers release removed controls. Summary, cost and original-intent edits share a quiet header action visible only while expanded. Original intent no longer asks for the initial plan; prior saved plan text stays in intent versions and survives edits/exports.

Validation includes a v14-to-v15 upgrade with existing labels and an active deletion fence, owner/origin and revision conflicts, removed choices, backup/restore of a custom owner and tag, browser creation/filtering/settings editing, header visibility, photo Save/reopen and alignment against the actual single-photo frame. No production data was deleted or restored for these checks.

The separate Manufacturer details disclosure was removed at the owner's request; Manufacturer and Mfg part number remain optional ordinary rows, with saved values retained. New custom parts/subassemblies default to an editor-only name link: Generic Part Name fills a read-only Specific Part Name. Uncheck to enter a separate name. Existing distinct names open unlinked; rechecking and unchecking restores the separate draft name. Description, purpose, manufacturer and specifications never link. The shortcut is inferred from the existing saved names when reopening; it adds no schema, background synchronization or changes to frozen revisions.


## Copy outside Cloudflare reminder

Data backup stores `backupReminder` in the existing global settings JSON, with absent fields defaulted for older installations/archives. No schema migration is needed. It contains `intervalDays` (integer 7–90, default 30), `lastDownloaded` (server completion timestamp, archive creation timestamp and manual/nightly source), `lastConfirmed` (server timestamp and known archive creation timestamp, otherwise null) and `snoozedUntil`. Normal owner/tag saves preserve reminder fields; reminder actions use bounded revision-checked retries so concurrent devices do not lose owner/tag edits. The settings editor refreshes the row revision only when its original owner/tag choices are unchanged.

`GET/POST /api/project-engine/backup-reminder` inherits the central and feature owner checks, same-origin mutation guard and private/no-store responses. Actions are `downloaded`, `confirm` (explicit confirmed=true), `snooze` (three days on the server clock) and `interval`. Client-supplied confirmation/completion times are not used. Reading a page never records a copy. The shared header checks on navigation, focus/visibility and once per minute for long-open pages. Signed-out responses hide the banner; failures do not block the notebook. The inline banner wraps at phone width, with no overlay or fixed positioning.

Downloads and confirmed outside copies remain separate. Direct manual and retained-nightly saves open the native file picker from the click and stream into it. The download record is written only after close resolves, followed by an explicit centered outside-copy confirmation showing the archive creation date. Failed/cancelled file writes abort, and nightly streams must match the retained copy's verified byte count before closing. If recording fails after a file was saved, the UI says the file was saved but the date/confirmation is unconfirmed. It does not retry the whole download or claim the backup failed. The site cannot observe Dropbox or the chosen destination. Browsers without direct-save support retain ordinary nightly download links with a clear completion-detection limitation and manual outside-copy confirmation.

The Download now link opens `website-settings.html#data-backup`; the disclosure opens, scrolls into view after asynchronous settings rendering, and the newest verified retained copy is marked. When none exists, Backup all data remains available on supported browsers. Whole-site backups include reminder settings through the existing complete database export; independent native D1/R2 restore tests recover the exact recorded dates and show an old record as overdue. Restoring never changes the acknowledgement to today. Individual project and Workshop-only exports do not replace the site reminder settings.

## Permanent project numbers

Projects have a server-assigned, immutable display number beginning at P1001. The editable name may be duplicated after an explicit UI confirmation. Numbers are separate from part/subassembly prefixes and the UUIDs that scope storage, URLs and command replay. Catalog cards/search, the project heading/tree, settings, delete confirmation and readable HTML show the number alongside the name.

Engine migration 17 creates a permanent `engine_project_numbers` ledger without a foreign key to deletable project content. Existing headers (including hidden/deleting ones) receive numbers once in creation order with UUID as a tie-breaker, without updating those headers. An AFTER INSERT trigger reserves the next global number in the same atomic transaction as normal creation or a private restore header. UNIQUE/range constraints and immutable update/delete triggers protect reservations. Project deletion retains only the reservation's UUID and number; there is no name or project content in the ledger. Cancelled/interrupted restores may leave a gap. Committed reservations never get recycled; rolled-back, unissued inserts reserve nothing.

Per-project exports retain the source number as metadata, while restoring a separate copy receives its own new reservation. Import into an independent database uses that destination’s number ledger; source display numbers are not allowed to claim or collide with local reservations. Older exports without a number remain readable. Whole-site export/restore includes all reservations, including deleted projects, and the schema triggers. A restore test verifies the next created project cannot reuse a deleted reservation after recovery. No existing project names, parts, photos or history are rewritten by the migration.

The duplicate-name prompt checks current owner-visible projects before create/rename, ignoring case and redundant whitespace. Change name returns focus to the retained draft; Keep same name explicitly permits the duplicate. A repeated unchanged save after an uncertain response retains that approval and replays the same command rather than allocating another project/number. Owner/prefix-only settings edits do not ask to approve an unchanged name. Names are intentionally not unique database keys; the number and UUID provide identity.


## Manufacturer field visibility

Current Part/Tool editors and detail views show Manufacturer/Mfg part number only for purchased physical items. Made-in-house items, assemblies, Documents and Code hide these controls; switching source/type does not clear saved values. Full Parts Management rows leave these cells empty for non-purchased items. Existing Workshop-linked selections without an explicit source are treated as purchased; an explicit made-in-house choice takes precedence. The Workshop catalog itself is unchanged. Historical configuration/revision displays and backup/export records retain their original manufacturer information, so earlier evidence is still available. This is a UI change with no schema or server save change.
