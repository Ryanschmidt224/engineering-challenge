# Electronics template rewrite

Owner request: rewrite every template under Electronics using DigiKey terminology. This change covers the 22 shipped families in the seven children of Electronics. Power, Motors, tools, hardware and owner-created families are outside that literal category scope. No manufacturer ratings are seeded.

## Release boundary

PR #106 (AI lookup and Edit template wording) is already deployed separately. Owner update Nov 25 ended routine/mandatory Claude reviews and supersedes older review gates in planning documents. This data-only Workshop migration 3 preserves saved values, IDs/types/units and owner customizations and may proceed after green exact-head checks. Particularly sensitive releases, such as irreversible project deletion, still need an owner prompt. This does not authorize held recovery draft #91.

## Terminology and field design

Labels follow DigiKey's product-selection guides; the descriptions are original application guidance. Generic IC and other-sensor templates deliberately remain general and explain when a more specific template is needed. Compound ratings and ranges use text so units, min/typ/max, temperatures and test conditions can remain together. Scalar numeric fields keep fixed units. Product specifications are visible by default rather than marked as normally entered later in a project. No missing value is replaced with zero, and no typical rating is fabricated.

MOSFET gate threshold is distinct from useful gate drive. Rds On includes Id/Vgs conditions. Current ratings retain temperature and continuous/peak distinctions. LED test current is separate from maximum continuous current. Switches separate AC/DC ratings; relays separate coil/control and contact/load ratings. Board input and GPIO voltages remain separate.

## Existing data and concurrency

- Released migrations 1 and 2 and their seed definitions are unchanged. Migration 3 operates on known starter-family IDs whose name/category still match and which are not archived. Renamed/archived/custom families are untouched.
- Every original field ID/type/unit remains. Labels/order/visibility/default-entry hints change only while all metadata still matches the original default. Owner-modified definitions remain unchanged. New definitions are additive, use deterministic IDs and do not duplicate an equivalent existing label/unit. Owner-deleted original definitions are not reinserted.
- Ambiguous legacy fields are retained with an explicit Legacy label. Unpopulated ones are hidden; populated ones stay visible for verification, including numeric zero and boolean false. Values are never copied into a differently defined rating. Product/use JSON, revisions, attachments, project instructions, files and backups are untouched.
- Templates that cannot fit within the existing 80-field cap are skipped entirely. A colliding new ID owned by another family also skips that template. Owner notes/descriptions are filled only when empty.
- Changed canonical family revisions increment, so old template/product editor tokens cannot overwrite the updated definitions. The complete migration and schema marker commit in one existing D1 batch. Every data statement checks that version 3 has not been committed, making a concurrent replay harmless.
- New empty databases end with 432 fields across the existing 60 families. There are 66 data statements; the largest is under 12 KB. No tables, columns, indexes, triggers, quotas, AI settings or cron jobs change.

## Rollback and older backups

The prior Worker understands all retained fields and existing types; rolling code back leaves the additive catalog upgrade in place. It does not reverse saved metadata. Use a verified Workshop export for an exact catalog restore into an isolated destination if needed. No restore implementation is changed: allSchemaStatements applies data statements to empty tables, then an old export restores exactly its own definitions. Its marker is current, so opening that restored catalog does not silently rewrite its historical template definitions.

## AI mapping

A unitless text destination may retain a source value with its units and conditions (for example an Rds On rating). Fixed numeric destinations still require identical units, with no conversion or range stripping. Open choice fields accept their existing free-text semantics. Unique exact-label suggestions only preselect empty destinations; replacement remains explicit and Save product remains separate.
