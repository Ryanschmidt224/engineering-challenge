## Legacy read-only boundary

Engine commands, accounts and Knowledge retain their existing boundaries. No data is imported or deleted and no migration is added by this change.

Legacy GET/HEAD behavior remains subject to its existing authorization; history, files and exports remain readable. Practice-to-Notes upgrade-on-read is skipped while read-only so browsing does not rewrite source evidence or create migration backups. Do not turn `canEditProject` into a blanket denial: legacy download/export readers also use it to authorize private access. The legacy UI shows a persistent read-only notice with a new Projects link and hides project creation/settings editing. Older cached tabs and remaining legacy edit controls receive `409 LEGACY_READ_ONLY`; the server boundary is authoritative.

## Automated acceptance

`scripts/preview-acceptance.mjs` runs the same functions as the deployed proof page through normal authenticated APIs. No separate test-account endpoint, auth bypass, direct SQL endpoint or automatic production migration is added. The owner-only, preview-gated `GET /api/project-engine/environment` returns only Cloudflare's runtime version identity and performs no database work.

Before proof writes, the script verifies the actual version's bindings with the read-only Cloudflare control-plane API. It requires source D1 `3314f42f-7c04-4798-99dc-b5b97c4fb82f`, independent target D1 `d761ae08-64f2-4130-8cfa-f596e8e89b80`, R2 `building-schmidt-photos-preview`, and the preview flag on both. A missing runtime identity, Cloudflare authorization error, unexpected binding, common source/target database or unsigned preview access fails before creating proof projects. A response that merely repeats configured binding variables is not accepted as binding verification.

The script checks production's disabled routes, deployed legacy read-only preservation on both previews, the guarded D1 proof and exact replay, custom-part and assembly/Workshop source proofs, independent recovery, file hashes/keys, and the final byte-for-byte unchanged-source check. Runtime version IDs are rechecked at phase boundaries. It retains synthetic projects and source files for inspection. It never deletes projects, modifies real engineering records, reseeds a database, or changes account/catalog permissions. The assembly proof creates its own clearly named Workshop family and two synthetic products.

The legacy check reads the owner catalog including archived entries, requires its explicit read-only flag, and sends `PATCH /api/projects` with only `{"visibility":"public"}`. That body is deliberately invalid even without the boundary (private visibility and a valid identity are required), so no real project edit is prepared. Acceptance requires `409 LEGACY_READ_ONLY`, then a byte-for-byte identical catalog response. Reports contain its SHA-256 and project count, not catalog contents. This verifies deployed catalog reads and save rejection; it does not claim a live download of every legacy project's export.

Run with Node 22 or later. Provision secrets through a trusted runner's secret store, never command arguments, Git, chat or printed logs:

- `CLOUDFLARE_API_TOKEN`: read-only Workers Scripts Read (or a supported narrower read permission), scoped to the relevant Cloudflare account/Worker.
- `SOURCE_SESSION_COOKIE` and `TARGET_SESSION_COOKIE`: sessions for the existing disposable preview owner, supplied securely by the operator through the trusted runner's secret store. Sign in through the normal preview site, use short-lived sessions for the explicit run, and sign out afterward. Session cookies are sensitive credentials: never paste them into chat, command arguments, files or reports.
- The runner accepts session cookies only. It does not accept owner email/password, perform login, or read password environment variables. Missing either session fails before any network request. The AI does not retrieve or handle the operator's password or browser cookies.

Reports contain runtime IDs, resource IDs and synthetic evidence, never credentials or the raw Cloudflare response. ## Read-only orphan inventory

After checking the exact preview version and isolated bindings, an existing owner session may call `GET /api/project-engine/maintenance/orphans?kind=restores&limit=25`. Other kinds are `files`, `values` and `objects`. Follow each response's `nextCursor` with the same kind/page size until it is null. Metadata cursors include project scope, so restored copies with identical child IDs are not skipped. Object cursors are opaque R2 continuation values. Limits are 1–50, default 25; large-project inventory query/latency limits are not measured capacity.

The response is explicitly `dryRun: true`, `executable: false`. This route has no POST/claim/apply operation and performs no engineering-data or object deletion. It shares the normal preview/owner gate and validated schema entry. Inventory protects file metadata/links, historical JSON references (including escaped IDs), catalogue attachments, recovery-owned objects, recent/unknown object ages and active/unknown restore progress. Inactive observations may qualify for an internal claim under the rules below, not immediate deletion. A malformed saved JSON field fails the report instead of producing false deletion candidates. A job with no published target/receipt cannot qualify for completed-staging cleanup.

Do not expand the remaining sweep under the schema-9 freeze. A future owner-pressed action after cutover must reuse existing object/key fencing and revalidate ownership/references with current project/schema tokens. Restore progress tracking and atomic retirement claims are implemented below. Delete only a claimed, unpublished hidden copy; preserve all source/published project rows, receipts and historical bytes. Journal progress and bound metadata/object batches; never scan/delete outside allowlisted project-owned namespaces. Test restore/upload/revision races, interrupted cleanup and retries. A report older than a concurrent save is not an apply plan. The inventory protects recent/unknown progress rather than treating an old creation date as abandonment.

### Restore activity and claims

Migration 7 implements the restore-side prerequisite. Existing jobs receive a fresh grace period at upgrade. Current metadata/loading batches refresh `last_activity_at`; slow input checks progress after 30 seconds, and a forced check precedes each restored-file write. Inventory may now report `inactive_restore_claim` with `observedActivity` when creation and last progress are both at least 24 hours old, no peer retry is active, no receipt exists and the target is absent or the same owner's matching hidden project. Unknown ages, current progress, published targets, foreign ownership and existing retirement remain protected. Tokens are not included in inventory.

`claimInactiveRestore` is an internal tested primitive, not an HTTP operation. It atomically rechecks the observation, peer activity, ownership/hidden marker, receipt and compiled schema before recording an immutable claim. A winning claim fences the entire owner/target/operation; a resume/heartbeat that wins first defeats the stale claim. Triggers protect staging, loaded engineering rows, job/header changes, receipts and replacement retry jobs, including older SQL paths. No source or published project is deleted or archived. Starting a new target/operation from the retained backup remains possible after retirement. The operator cannot invoke claims through the GET inventory route; POST/apply still returns 405.

Migration 8 adds a permanent retired-file-key journal. The internal `cleanupRetiredRestore` executor requires an exact owner/job/claim receipt and rechecks the compiled schema, matching hidden marker (or absent target), all operation receipts and completed peers in every mutation batch. It journals only exact target/operation restored-file keys before removing private rows, in dependency order, at most 100 rows / roughly 512 KB per mutation (one larger supported row is allowed), with 1–20 mutation batches per invocation. Retried calls resume from the remaining rows. It retains jobs, claim tokens, key tombstones and all R2 bytes. No HTTP/cron caller exists, and inventory remains non-executable.

Current upload, Workshop-copy and restored-file writers check key fences around storage writes. Database triggers also block older file metadata/staging admissions that reuse a retired key. An R2 put already in flight can still leave unlinked bytes; the post-put check prevents a successful transfer response, and metadata fences prevent publication. Migration 9 adds the internal retired-restore storage companion described next; it is not enabled for live use. Upload/Workshop orphan and frozen-value deletion are still unimplemented. Measure these added queries and cleanup batches in the real-D1 capacity run. Keep both preview hosts on compatible schema-9 handlers, or disable the engine; older deployed readers/writers are not made compatible merely by adding triggers. Never remove ledger entries or permanent job/key tombstones to bypass a version gate.

A future-schema check at request entry and inside command admission does not retroactively update older deployed versions; compatible readers/writers remain an operator cutover gate. ### Retired restore storage companion (migration 9)

`cleanupRetiredRestoreObjects` is internal only, exported by the common cleanup owner. It has no HTTP/cron caller. It requires the exact owner/job/claim receipt, current schema, an absent target header, no target receipt or completed peer, and no remaining staging in the claimed operation. It scans only that claim's immutable key journal in pages of 1–25 keys; it never lists a bucket. Only exact `project-engine/restored/<target>/<operation>/<file UUID>` destinations qualify. Retirement, key journaling and object upload must each be at least 24 hours old. Unknown ages, ETags or sizes stay protected.

Deletion intent and fresh global root checks are one atomic D1 statement. Existing engine file metadata, structured historical JSON (including Unicode-escaped keys), all staged files/nested engineering JSON and any existing Workshop attachment root protect bytes; malformed metadata fails closed. After intent wins, new engine/staged JSON roots to that key are refused by migration-9 triggers, closing the D1-check/R2-delete race. This is restricted to never-published destinations: legitimate exported backups cannot contain these destination storage identities. Original backup JSON, published/source bytes and independently restored file keys remain compatible and unchanged. Current Workshop writers create only `workshop-v2/files/` keys or URL attachments and cannot adopt a retired engine key; any later import/adoption feature must preserve that namespace boundary or add the same atomic reference fence before enabling this cleanup.

The helper checks ETag, size and upload time again before requesting key deletion. R2 deletion is by key, not an atomic conditional ETag delete: a previously in-flight put can still race it, but permanent metadata/reference fences prohibit publication. Results record the observed ETag, not a guarantee of permanent absence. Delete errors are retryable; an interrupted page may already have removed earlier keys. Per-ETag intents, key journals and job tombstones remain permanently. Every later sweep must restart journal pagination to discover late unlinked puts, including keys previously absent/deleted. Recent or changed objects defer to a later sweep; there is no terminal deleted marker that could hide them.

This implements only retired-restore storage cleanup. Prepared uploads, failed Workshop-copy storage and unreferenced frozen values remain unimplemented and deferred under the schema-9 freeze. No live object cleanup was executed. Exact-head review, compatible versions on both preview hosts and measured real-platform cost remain prerequisites to live maintenance. Do not infer those from disposable SQLite/R2 tests.
